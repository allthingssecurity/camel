== Summary

`camel-chaos` lets a developer, or an AI tool, turn on faults in a running Camel application and see how its routes
cope. A rule such as "fail 30 % of the sends to `kafka:orders` for one minute" or "stall route `poller` for 20 s" is
added while the application runs, and a report then says per route how many messages completed, failed, were handled
by the error handler, were redelivered or were lost, with a verdict.

With the `camel-chaos` JAR on the classpath its hooks are installed and stay idle until a rule is added. Without the
JAR, as in production, nothing of it is there. Faults run in real time, so a person can start an application, turn
chaos on and watch what happens, and the same rules can run inside a `camel-test-dst` world in virtual time.

== Motivation

Routes are written for the happy path, and their error handling is rarely exercised before production. Questions such
as "what happens to the messages in flight when the broker is slow for 30 s", "does this `onException` really match the
error the HTTP endpoint returns" or "does the consumer resume after its route was suspended" are answered today by
hand-written tests, one route and one fault at a time.

A prototype (CAMEL-26330 links it) showed the value: with rules on `to` only, it reproduced CAMEL-25684 (camel-slack,
a route suspend in the middle of a poll) and CAMEL-25682 on the code from before their fixes. The recent "remove a
route" bugs (CAMEL-26286, CAMEL-26288, CAMEL-26302 to CAMEL-26305: one route goes, and another route loses the cache
or channel it shares) have a shape a chaos rule can produce on demand.

AI tools that write and change routes need the same: a way to try a route against failures and read a short, honest
result.

== Goals

- Out of the box chaos for any Camel application in development: faults on sends, on processing steps, on messages,
  on consumer polls and on the route lifecycle.
- Switched on by the classpath, idle until a rule is added, rules added and removed live.
- Configuration through `camel.chaos.*` options of camel-main, as for `camel.debug.*` and `camel.trace.*`.
- A report per route with counts and a verdict, readable by a person and by a tool.
- Control from the CLI (`camel cmd chaos`), a dev console, and the camel-jbang MCP server.
- Real time by default; the same rules in virtual time inside a DST world.
- A seed makes a run repeatable.

== Non-goals

- Production use. With profile `prod` chaos stays off even when the JAR is present.
- Custom fault types written by users. The first version has a fixed set; a plugin SPI (a JAR with its own faults) can
  come later.
- Faults outside Camel: network partitions, killing processes, disk or clock faults of the host. Tools outside Camel
  do that; this is about what Camel does with the failures it sees.
- Changes to the routing engine. Every hook below uses an existing SPI.

== Proposal

=== Switched on by the classpath

`camel-chaos` registers a `ContextServicePlugin` (`META-INF/services/org.apache.camel.spi.ContextServicePlugin`), so
the `CamelContext` loads it when the JAR is on the classpath, the same way `camel-debug` turns the debugger on. The
plugin installs the hooks below while the context starts and before the routes are created. Each hook asks the
`ChaosManager` whether a rule matches; with no rules that is one volatile read, and the call goes on unchanged.

When the profile is `prod`, or `camel.chaos.enabled=false`, the plugin installs nothing.

=== Options

[cols="1,1,3"]
|===
|Option |Default |Description

|`camel.chaos.enabled` |`true` |Install the hooks (only when the JAR is present, and never with profile `prod`).
|`camel.chaos.seed` | |Seed of the random choices; without it a seed is picked and shown in the report.
|`camel.chaos.rules` | |Rules to add at startup, in the same text form as `camel cmd chaos add`.
|`camel.chaos.maxDuration` |`10m` |Upper bound for every rule; a rule without its own limit ends after this.
|`camel.chaos.reportOnShutdown` |`true` |Log the report when the context stops.
|===

They are a `ChaosConfigurationProperties` group in camel-main, so the catalog and tooling know them.

=== Rules

A rule has a target, a fault, how often it fires, and when it ends:

[source]
----
target:  route=<id or pattern> | endpoint=<uri pattern> | component=<name> | step=<processor id pattern>
fault:   error | delay | stall | drop | corrupt | lifecycle   (with parameters, see below)
rate:    a probability (0.3), or every Nth match
until:   a number of matches, a duration, or removed by hand
----

Rules are added, listed and removed live. A rule ends by itself after its count or duration (at most
`camel.chaos.maxDuration`), so a forgotten rule cannot keep breaking a dev instance.

=== Hooks at all levels

[cols="1,2,2"]
|===
|Level |Hook |Faults

|Sends to endpoints
|The component, wrapped where the component resolver creates it, as `camel run --stub` swaps in the stub component
there. The wrapper creates producers and consumers that go through chaos and delegate to the real ones.
|An exception of a given type, a delay, a dropped send that reports success, a changed message.

|Processing steps
|An `InterceptStrategy` added to the context, which wraps each processor of the routes.
|A delay or an exception at a step.

|Messages
|The same wrappers, on the message they pass on.
|Header values with random data, a body in an unusual charset, an `InputStream` that ends too soon.

|Consumer polls
|The `PollingConsumerPollStrategy` of a `ScheduledPollConsumer`, which runs around every poll; event-driven consumers
through the wrapped component.
|A failed poll, a slow poll, a poll that finds nothing.

|Route lifecycle
|The `RouteController`.
|Stall a route (suspend, then resume), stop and start it, remove it and add it again.
|===

The component wrapper is the hook for sends because it sees every send whatever started it: `to`, `toD`, `wireTap`,
`enrich`, `recipientList`, `multicast` and a `ProducerTemplate`. Two other places were considered:
`ExchangeSendingEvent` fires for every send but cannot stop it, because an exception thrown by an event notifier is
logged and ignored; `interceptSendToEndpoint` can stop a send but adds processors to the routes, which changes what the
user sees in route diagrams and in the route model.

A fault has a real type where it matters, so that the `onException` of the route is what gets tested: for the HTTP
components, an `HttpOperationFailedException` with a status code and headers; for any other endpoint, an exception
class and message given in the rule.

=== Time

The clock reads and the sleeps of `camel-chaos` (delays, stall durations, rule expiry) go through `TimeSource`
(camel-util, CAMEL-25911). By default that is the system clock, so a person sees a 20 s stall last 20 s. Inside a
`camel-test-dst` world the same rules run on the virtual clock: a 10 minute stall takes milliseconds, and a seed gives
the same report again, times included. The Javadoc of `TimeSource` calls it internal; this document records that
`camel-chaos` may use it, as `camel-test-dst` does. Chaos does not need DST.

=== The report

The plugin counts per route, from the exchange events: completed, failed, handled by the error handler, redelivered,
and the faults that fired. A rule can carry an expectation ("route `orders` completes 100 more messages"), which
finds messages that were lost before they became an exchange.

The verdict is PASS when every message the route took in completed or was handled, and FAIL otherwise, with the
reason. It must not call a message lost when its consumer redelivers it (a file that stays in the directory, a
transacted JMS message that is rolled back), because a tool acts on what the report says. The report is plain text
for the CLI and JSON for tools, and states the seed and the rules that were active.

=== Control

- A `chaos` dev console: list, add and remove rules, and show the report. The CLI connector uses it, so
  `camel cmd chaos add|list|remove|report` works against any running application with the JAR.
- The camel-jbang MCP server gets tools for the same (add a fault, report, clear), in a runtime tool group that is
  offered only when the application has `camel-chaos`.
- JMX is not needed for the first version.

=== Order of work

Each step is its own pull request after this document:

. The module, the plugin, the options, the rule model, the report, and the send hook through the component wrapper.
. The dev console and `camel cmd chaos`.
. Step, message and poll hooks.
. Route lifecycle faults.
. MCP tools.
. A DST world that runs chaos rules in virtual time, as an example and a regression test.

== Alternatives considered

- *Faults from outside the JVM* (a proxy in front of the broker, killing containers). Useful, but it cannot fail one
  route and not another, cannot produce a typed exception for `onException`, and needs infrastructure a developer
  running `camel run --dev` does not have.
- *Advice-with in tests.* It changes routes for one test; chaos is for a running application, and does not change the
  routes.
- *A change to the routing engine* (a fault hook inside the pipeline). Not needed: the SPIs above reach every level.

== Compatibility

Nothing changes for applications without the JAR. With the JAR and no rules, the hooks are installed but idle; the
cost is a wrapper per component and an intercept per processor, a development-time cost only. The new options are in
a new group.

== Risks

- The JAR left on the classpath of a production build. Mitigations: the `prod` profile guard, a WARN at startup when
  the hooks are installed, and rules that expire.
- A wrapped component that behaves differently from the real one (for example a component that checks the type of
  its own producer). The wrapper must delegate everything it does not change; components that cannot be wrapped are
  listed and skipped.
- A verdict that is wrong. The report states what it counted and from where, so a person can check it.

== Open questions

. Module location: `components/camel-chaos`, next to `camel-debug`, or under `dsl/camel-jbang`?
. Should the component wrapper be a small SPI in camel-main (a `ComponentResolver` decorator) shared with
  `camel run --stub`, or stay inside `camel-chaos`?
. Is the rule text form above good enough for `camel.chaos.rules` in `application.properties`, or should rules be
  YAML?
