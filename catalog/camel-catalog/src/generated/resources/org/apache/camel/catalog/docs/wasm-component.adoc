*Since Camel {since}*

*{component-header}*

https://webassembly.org[WebAssembly (Wasm)] is a low-level bytecode format designed as a portable target for the compilation of high-level languages like C, C++, and Rust, enabling deployment on the web for client and server applications.

This component provides support to leverage Wasm functions for message transformation.
It can either call an exported function of a module (the default `function` mode), or run a
https://wasi.dev[WASI] program, such as a Rust, Go or C program compiled to `wasm32-wasip1`, as a
sandboxed processor (`mode=wasi`).

Maven users will need to add the following dependency to their `pom.xml`
for this component:

[source,xml]
----
    <dependency>
        <groupId>org.apache.camel</groupId>
        <artifactId>camel-wasm</artifactId>
        <version>${camel-version}</version>
    </dependency>
----

== URI format

----
wasm://functionName?[options]
----

In `wasi` mode the path is not a function name: it is passed to the program as its name (argument zero).

== Usage

=== Writing A Wasm processor

In _Wasm_, sharing objects between the host, in this case the _JVM_, and the _Wasm_ module is deliberately restricted and as of today, it requires a number of steps:

1. From the _host_, call a function inside the webassembly module that allocates a block of memory and returns its address, then save it
2. From the _host_, write the data that should be exchanged with the _Wasm_ module to the saved address
3. From the _host_, invoke the required function passing both the address where the data is written and its size
4. From the _Wasm_ module, read the data and process it
5. From the _host_, release the memory when done

==== Providing functions for memory management

The module hosting the function *must* provide the functions to allocate/deallocate memory that *must* be named `alloc` and `dealloc` respectively.

Here's an example of the mentioned functions implemented in https://www.rust-lang.org[Rust]:

[source,rust]
----
pub extern "C" fn alloc(size: u32) -> *mut u8 {
    let mut buf = Vec::with_capacity(size as usize);
    let ptr = buf.as_mut_ptr();

    // tell Rust not to clean this up
    mem::forget(buf);

    ptr
}

pub unsafe extern "C" fn dealloc(ptr: &mut u8, len: i32) {
    // Retakes the pointer which allows its memory to be freed.
    let _ = Vec::from_raw_parts(ptr, 0, len as usize);
}
----

==== Data shapes

It is not possible to share a Java object with the Wasm module directly, and as mentioned before,
data exchange leverages Wasm's memory that can be accessed by both the host and the guest runtimes.
At this stage, the data structure that the component exchange with the Wasm function is a subset of the Apache Camel Message,
containing headers the body encoded as a base64 string:

._Java-only: data exchange wrapper class for Wasm module communication_
[source,java]
----
public static class Wrapper {
    @JsonProperty
    public Map<String, String> headers = new HashMap<>();

    @JsonProperty
    public byte[] body;
}
----

==== Data processing

The component expects the processing function to have the following signature:

[source,rust]
----
fn function(ptr: u32, len: u32) -> u64
----

* it accepts two 32bit unsigned integers arguments
** a pointer to the memory location when the input data has been written (`ptr`)
** the size of the input data (`len`)
* it returns a 64bit unsigned integer where:
** the first 32bit represents a pointer to the return data
** the last 31bit represents the size of the return data, which must have the same data shape discussed above unless there is an error (see below)
** the most significant bit of the returned data size is reserved to signal an error, so if it is set, then the return data could contain an error message/code/etc

Here's an example of a complete function:

[source,rust]
----
#[derive(Serialize, Deserialize)]
struct Message {
    headers: HashMap<String, serde_json::Value>,

    #[serde(with = "Base64Standard")]
    body: Vec<u8>,
}

#[cfg_attr(all(target_arch = "wasm32"), export_name = "process")]
#[no_mangle]
pub extern fn process(ptr: u32, len: u32) -> u64 {
    let bytes = unsafe {
        slice::from_raw_parts_mut(
            ptr as *mut u8,
            len as usize)
    };

    let mut msg: Message = serde_json::from_slice(bytes).unwrap();


    let out_vec = serde_json::to_vec(&msg).unwrap();
    let out_len = out_vec.len();
    let out_ptr = alloc(out_len as u32);

    unsafe {
        std::ptr::copy_nonoverlapping(
            out_vec.as_ptr(),
            out_ptr,
            out_len as usize)
    };

    return ((out_ptr as u64) << 32) | out_len as u64;
}
----

=== Running WASI programs

With `mode=wasi` the module is a WASI preview1 _command_: a program with a `_start` entry point, as produced by
`cargo build --target wasm32-wasip1` for a Rust binary crate, `GOOS=wasip1 GOARCH=wasm go build` for Go, or
`clang --target=wasm32-wasip1` with the WASI SDK for C. No camel-wasm specific code is needed in the program.

For every exchange the component runs the program once, on a fresh instance:

* the message body is the program's standard input (an empty body is an empty input),
* what the program writes to standard output becomes the message body (as `byte[]`); other headers are kept,
* the exit code is stored in the `CamelWasmExitCode` header; a non-zero exit code fails the exchange with a
  `WasiExitCodeException` and leaves the body unchanged, unless `failOnNonZeroExit=false`,
* what the program writes to standard error is stored in the `CamelWasmStderr` header (at most 8 KiB) and logged
  at DEBUG level,
* a trap (for example a Rust panic) fails the exchange with the runtime's `TrapException`.

Here is a complete Rust program that upper-cases its input:

[source,rust]
----
use std::io::{self, Read, Write};

fn main() {
    let mut input = String::new();
    io::stdin().read_to_string(&mut input).expect("read stdin");
    io::stdout().write_all(input.to_uppercase().as_bytes()).expect("write stdout");
}
----

Built with `cargo build --release --target wasm32-wasip1` (after `rustup target add wasm32-wasip1`), it is used as:

==== What the program can access

A WASI program only gets what the route gives it:

* *Arguments*: the endpoint path as argument zero, then the `args` option, split on whitespace (use double quotes
  around an argument that contains spaces). Arguments are fixed by the route and cannot be set from headers.
* *Environment variables*: only those configured with `environment.NAME=value`, plus the headers listed in
  `environmentHeaders`, each passed under its own name. Message headers usually come from whoever sent the message,
  so none is passed unless it is listed. The JVM's own environment is never passed.
* *Files and network*: none. There are no preopened directories, so the program cannot open any file, and socket
  calls fail.
* *Clock and random numbers*: the host's.

==== Notes

* The program runs to completion for every exchange, so it keeps no state between exchanges and concurrent
  exchanges never share an instance. Programs with a long start-up (the Go runtime, for example) pay that cost on
  every exchange; see `compile` below.
* Standard output is buffered in memory until the program exits.
* The `wasm` language does not support `wasi` mode.

=== Limits

Both modes support two limits, which protect the route from a module that misbehaves on some input:

* `maxMemoryPages`: the maximum size of the module's linear memory, in 64 KiB pages. Rust, Go and C toolchains
  declare no maximum by default, which lets a module grow to 4 GiB of JVM heap. When the limit is reached, memory
  growth fails inside the module, which usually traps or exits with an error.
* `timeout`: the maximum time, in milliseconds, one invocation may run. When it is exceeded, the module is interrupted
  and the exchange fails with an `ExchangeTimedOutException`. With a timeout the module runs on a separate thread.

Instruction counting ("fuel") is not supported by the runtime; use `timeout` instead.

In `function` mode one instance of the module serves every exchange of the endpoint, one at a time. After a trap or
a timeout that instance is discarded and the next exchange gets a fresh one, so any state the module kept in its
memory or globals is lost.

=== Compiling the module

By default the module is interpreted. With `compile=true` it is translated to JVM bytecode once, when the endpoint
starts, which typically makes it an order of magnitude faster at the cost of a slower start and more metaspace. Both
limits apply to compiled modules as well.

=== Security

The module is code chosen by the route author, and like any other route code it is trusted: it runs in the JVM with
the WebAssembly sandbox around it, but the component does not protect against a malicious module. The message
body and headers are untrusted input, and the defaults keep them away from anything the module could misuse: in
`wasi` mode no headers become environment variables unless they are listed in `environmentHeaders`, arguments cannot
come from headers, and the program has no file system or network access. Use `maxMemoryPages` and `timeout` to bound
the memory and time a module can use for one message.
